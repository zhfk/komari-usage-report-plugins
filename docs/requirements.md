# Komari 日报与周报插件开发需求文档

> 状态：待开发；本文整理自需求附件。文中涉及 Komari 的接口、运行时、权限及通知行为均为待核查要求，不代表已经验证或实现。

## 一、项目概述与范围

**产品名称：** Komari Daily & Weekly Reports  
**插件标识：** `komari-daily-weekly-reports`  
**技术方向：** TypeScript 开发，编译为目标 Komari 插件运行时支持的 JavaScript。  
**运行方式：** 通过 Komari 插件管理界面安装、配置和启用。  
**通知渠道：** Telegram，优先复用 Komari 已配置的通知系统。

开发可安装、配置、运行和测试的服务器监控报告插件，按自然日和自然周汇总流量、网络延迟、在线率、上下线、告警、到期与续费事件。范围仅包括日报和周报，不包括月报。

**核心业务要求：即使统计周期内没有任何异常，也必须按计划发送报告。** 数据不足时不得误报正常；数据全部不可用时仍应尝试发送明确的失败提示。

交付物包括可运行的源代码、兼容的插件清单及可安装 ZIP、中文配置与管理功能、报告模板、历史指标与事件持久化、调度和重试机制、自动化测试，以及中文安装、升级和故障排查文档。实际支持能力以技术核查和目标版本验证为准。

## 三、报告类型与发送计划

只开发日报和周报，不需要月报。

### 3.1 日报

默认发送时间：

每天 23:59，时区 `Asia/Shanghai`。

统计范围：

发送当天的 00:00:00（包含）至实际统计/发送时点（不包含），按配置时区计算。

例如：

2026-11-12 23:59 发送的日报，统计 2026-11-12 00:00 至 23:59 的当日数据。

日报属于发送当天，不顺延到前一天，也不使用滚动 24 小时窗口。历史日期补发统计所选完整自然日；周报仍统计上一完整自然周。

### 3.2 周报

默认发送时间：

每周一 09:00，时区 `Asia/Shanghai`。

统计范围：

上周一 00:00:00（包含）至本周一 00:00:00（不包含）。

例如：

2026-11-16 09:00 发送的周报，统计 2026-11-09 至 2026-11-15 的完整自然周。

### 3.3 调度功能

日报和周报分别支持：

- 独立启用或禁用。
- 自定义发送时间。
- 自定义时区，默认北京时间。
- 手动立即发送。
- 预览报告。
- 指定历史日期补发。
- 发送记录查询。
- 失败自动重试。
- 防止同一周期重复自动发送。

必须使用可靠的日期和时区计算。

Cron 调度时区可能不同于报告时区，应正确处理。

不要假设修改插件配置中的时区字段就能自动改变 Cron 运行时区。

建议使用一个可靠的周期检查任务，根据配置时区判断报告是否到期，结合持久化发送状态实现去重和失败补发。

插件重启后应恢复调度状态。

## 四、极其重要：无异常也必须发送报告

这是不可妥协的核心需求。

每天和每周，无论是否发生告警，都必须发送报告。

### 正常情况下

如果统计周期内：

- 没有离线事件；
- 没有 CPU 告警；
- 没有内存告警；
- 没有磁盘告警；
- 没有异常延迟；
- 没有服务到期提醒；
- 没有续费事件；

仍然必须生成并发送日报或周报。

报告应明确展示：

- 📊 当期流量情况
- 📡 网络延迟情况
- 🟢 在线情况
- ✅ 监控事件：未发现异常
- 🖥️ 服务器运行概况
- 📅 统计时间范围

例如：

✅ 今日未发现监控异常

📡 网络监控正常

🖥️ 所有被监控服务器运行正常

📨 本报告由 Komari 自动生成

### 不允许的实现

禁止写成：

`if (alerts.length === 0) return;`

禁止只有发生事件时才发送报告。

禁止因为流量为零就跳过报告。

禁止因为部分节点没有监控数据就直接丢弃整份报告。

### 必须区分三种情况

1. 正常：已成功采集数据，未发现异常。
2. 异常：已成功采集数据，发现监控异常。
3. 数据不足：部分或全部数据无法获取，无法确认是否异常。

**没有采集到数据，不等于服务器正常。**

如果无法确认监控结果，应显示“数据不足”或“监控状态未知”，不能错误显示“全部正常”。

如果所有监控数据都读取失败，也应尝试发送一条明确标注“统计失败/数据不可用”的报告，确保用户知道监控系统存在问题。

## 五、服务器流量统计

必须按照每台服务器分别统计：

- 上传流量。
- 下载流量。
- 总流量。
- 所有服务器汇总流量。
- 当前报告周期与上一同类周期的变化百分比。
- 周报中的流量使用排名。

单位自动转换：

B、KB、MB、GB、TB。

默认使用 1024 进制，并在代码中统一单位定义。

流量计算规则：

1. 核实 Komari 原始指标是累计计数器、时间桶增量还是速率数据。
2. 根据真实数据语义计算流量。
3. 若为累计计数器，处理回绕、重启与计数器重置。
4. 不允许把累计计数器数值直接求和。
5. 不允许把网络速率直接当成流量。
6. 对缺失数据、重复时间戳及异常值进行处理。
7. 对时段边界的数据覆盖度给出判断。
8. 不能准确计算时显示“数据不足”或“估算值”。
9. 所有服务器的汇总应避免重复计数。

若 Komari 的网络指标不支持可靠的自然日增量计算，应尝试使用官方支持的账单流量或聚合接口，并记录选择该接口的理由。

## 六、网络 Ping 和延迟统计

针对每台服务器及其关联 Ping 任务，统计：

- 平均延迟。
- 最低延迟。
- 最高延迟。
- Ping 成功次数。
- Ping 失败次数（若有可靠数据）。
- 丢包率（若可计算）。
- 延迟超过阈值次数。
- 网络质量状态。

推荐默认阈值（均允许修改）：

- 平均延迟警告阈值：200 ms。
- 单次延迟告警阈值：300 ms。
- 丢包率警告阈值：5%。

上述阈值仅作为插件默认值，不代表所有地区网络质量的统一标准。

Ping 结果必须按任务区分，不能将不同目标的 Ping 混成一个无法解释的平均值。

需要考虑：

- Ping 任务启停。
- 不同任务探测频率。
- 探测数据缺失。
- 节点离线期间探测中断。
- 探测失败与未采集的区别。
- 历史数据保留时间。
- 聚合数据的精度限制。

禁止根据空数组推导 0% 丢包。

如果 Komari 的接口只提供有效延迟样本，而没有失败次数，则丢包率必须标记为“无法计算”。

报告中应注明异常统计和数据覆盖情况。

## 七、服务器在线率与离线事件

需要统计：

- 各服务器在线率。
- 全部节点的综合在线率。
- 离线次数。
- 总离线时长。
- 最长离线时间。
- 离线与恢复时间。
- 周报中的节点稳定性排名。

优先使用可靠的上下线历史事件或有明确语义的时间序列。

计算示例：

在线率 = 有效在线时长 / 有效监控时长 × 100%

需要正确处理：

1. 离线发生于统计周期之前，恢复发生于周期内。
2. 离线发生于统计周期内，恢复发生于周期之后。
3. 长时间离线跨越多个自然日。
4. 服务器长期离线未恢复。
5. Agent 重启。
6. Komari 服务端停止运行。
7. 插件重启造成的事件采集缺口。
8. 重复上线和离线事件。
9. 不同节点加入监控系统的时间不同。

不要把监控系统无法采集数据的时间直接算为服务器离线。

如果无法准确计算，应标注统计可信度和数据缺口。

## 八、CPU、内存、磁盘和性能告警

每日和每周统计：

- CPU 使用率告警。
- 内存使用率告警。
- 磁盘使用率告警。
- 系统负载告警。
- 其他 Komari 支持的告警。

每条告警尽量记录：

- 时间。
- 服务器 UUID。
- 服务器名称快照。
- 告警类型。
- 告警等级。
- 告警内容。
- 恢复时间。
- 持续时间（只有依据充分时才计算）。

日报尽量显示完整的重要事件列表。

周报主要展示：

- 告警总次数。
- 告警类型分布。
- 受影响节点数。
- 最严重的告警。
- 重复告警最多的服务器。

如果无法取得原生告警恢复事件，应明确显示“恢复时间未知”，禁止编造。

## 九、服务到期与续费事件

支持以下事件：

- `Expire`
- `Renew`

统计：

- 当期到期提醒次数。
- 当期自动续费事件。
- 受影响服务器。
- 事件时间。
- 事件详细信息。

若能够从可靠的官方数据获取到期日期，可增加：

- 剩余天数。
- 到期时间。
- 即将到期的服务器列表。

不要根据任意文本推断续费一定成功。

需要区分“续费触发”“续费成功”和“无法确认续费结果”。

不可凭空生成到期日期或续费状态。

## 十、事件捕获与持久化

需要研究 Komari 对以下通知事件的支持：

- `Offline`
- `Online`
- `Alert`
- `Renew`
- `Expire`
- `Test`

注意：具体大小写和事件数据结构必须根据运行版本确认。

同时加入插件内部事件：

- `DailyReport`
- `WeeklyReport`
- `ReportFailure`

优先选择官方支持的事件订阅机制。

如果不存在官方事件订阅机制，可考虑：

1. 使用经过验证的插件 Hook。
2. 配合现有通知 JavaScript 模板进行事件转发。
3. 使用受保护的插件路由接收事件。
4. 在官方支持范围内使用其他可靠方式。

不得虚构事件监听接口。

事件转发方案必须提供完整的配置代码和安装说明。

不得破坏现有 Telegram 即时告警。

事件数据应保存在插件持久化目录中，并在插件升级后继续保留。

建议至少保留 90 天的事件记录，默认保留 180 天，支持配置。

存储字段至少包含：

- 事件 ID。
- 原始事件类型。
- 规范化事件类型。
- 事件时间。
- 接收时间。
- 节点 UUID。
- 节点名称。
- 事件内容。
- 来源。
- 去重指纹。
- 可选恢复关联 ID。

事件系统应支持：

- 去重。
- 跨天统计。
- 时间顺序排序。
- 数据库重启恢复。
- 事件清理。
- 错误日志。
- 数据导出。
- 数据备份。

不得在持久化事件中保存 Agent Token、Telegram Token 或其他不必要的敏感字段。

**必须防止日报和周报自身被当作普通告警事件重新记录，从而引起重复通知或循环发送。**

## 十一、用户当前 Komari 指标保留配置

当前计划采用：

| 指标类型 | 保留数值 | 保留时长 |
|---|---:|---|
| 1 分钟桶 | 4320 分钟 | 3 天 |
| 5 分钟桶 | 14400 分钟 | 10 天 |
| 1 小时桶 | 600 小时 | 25 天 |

这是本项目的默认部署环境，不要擅自要求用户改成 90 天或 180 天。

插件需要适应上述数据保存策略。

日报优先使用分钟级数据。

周报优先使用适合整个周期的较高精度数据。

为了提高可靠性，建议插件每天生成并持久化每个节点的聚合统计结果，周报可以基于经过校验的日统计结果汇总。

要求：

- 避免重复查询大量历史记录。
- 避免超大查询造成内存增长。
- 对查询结果分页或按日期、节点分批。
- 正确处理聚合时间桶与统计日期边界。
- 处理重启后错过每日聚合的情况。
- 记录源数据采样数量及覆盖情况。
- 对缺失聚合数据执行可行的历史补算。
- 当底层历史数据已被清理时，不允许伪造数据。

注意：指标桶保留策略不一定控制 Ping 历史和通知事件的保留时间。必须单独核查并处理。

## 十二、Telegram 通知方案

优先使用 Komari 自身通知系统。

尽量通过官方 `admin:sendNotification` RPC 发送自定义报告事件。

复用现有 Telegram 通知设置，不要求用户再次输入 Bot Token 或 Chat ID。

如果官方通知系统不支持所需的多行格式、消息长度或发送确认机制，应给出兼容方案。

只有在经过验证无法满足需求时，才允许增加独立 Telegram 配置，并解释原因。

### 通知格式要求

- 中文简体。
- 适量 Emoji。
- 清晰的报告标题。
- 明确的统计周期。
- 服务器名称清晰。
- 上传与下载分开显示。
- 延迟和在线率分开显示。
- 异常事件按时间排序。
- 重要异常突出。
- 无异常时明确表示“未发现异常”。
- 数据不足时突出显示。
- 不能暴露服务器 IP、Token 等敏感信息（除非明确配置允许展示 IP）。

优先使用 Telegram HTML 格式。

所有动态文本必须经过正确的 HTML 转义。

处理 Telegram 单条消息长度限制，必要时分段发送。

优先保证重要统计内容先发送，再发送详细事件列表。

分段发送的多条消息需显示正确的分页序号，并有失败重试及部分发送状态记录。

## 十六、可靠性与异常处理

插件必须适合长期无人值守运行。

### 调度与重启

- Komari 重启后自动恢复。
- 插件升级后保留历史事件和报表。
- 防止调度任务重复注册。
- 防止同一报告周期重复发送。
- 自动检测上次错过的报告。
- 对超期补发设置可配置策略。
- 不得无限补发导致 Telegram 消息轰炸。

### 发送失败

需要区分：

- 报告生成失败。
- 数据读取失败。
- 通知 RPC 调用失败。
- Telegram 返回失败。
- 发送结果无法确认。
- 消息分段部分成功。

提供合理的指数退避重试或类似机制。

必须避免因不确定的网络结果而盲目重发，造成重复消息。

请明确说明通知系统能提供怎样的成功确认语义。

若只能确认 Komari 接受了发送请求，而不能确认 Telegram 实际投递，应在日志中准确反映，而不是声称已送达。

### 持久化

记录至少包含：

- 报告类型。
- 周期起止时间。
- 报告生成时间。
- 报告内容摘要。
- 发送状态。
- 重试次数。
- 最后一次错误。
- 发送完成时间。
- 去重键。
- 数据完整性状态。

建议使用原子写入或事务机制，防止重启时破坏数据。

禁止只通过内存变量防重复。

## 十七、性能与安全要求

插件不能明显影响 Komari 主程序稳定性。

必须遵循最小权限原则。

只有确实需要时才申请：

- `allowSystemRPC`
- `allowRoutes`
- `node`

不要默认申请：

- `allowExec`
- `allowAllFileAccess`
- `allowListen`
- `allowHTMLInject`
- `allowHooks`

如需其中某项权限，必须解释用途并优先寻找低权限替代方案。

性能要求：

1. 不阻塞主线程执行长时间同步任务。
2. 避免一次将所有历史数据加载到内存。
3. 合理限制并发查询。
4. 控制存储文件大小。
5. 限制日志数量及保留时间。
6. 避免无限定时器、无限递归和忙等待。
7. 处理 API 限流和错误。
8. 避免未经鉴权暴露内部事件接收接口。
9. 避免任意路径写入和日志注入。
10. 对节点名称、告警内容等动态字段进行安全处理。

如使用事件接收 HTTP 路由，必须验证鉴权方式、签名或共享密钥，并禁止公开无保护的写入接口。

不要泄露 Komari 管理员 API Key、Telegram Bot Token 或其他凭据。
