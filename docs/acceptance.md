# 需求核对与验收记录

版本：0.1.0-beta.1。核对日期：2026-11-12。

这里区分“已实现并模拟验证”“以有明确限制的兼容方式实现”“待真实环境验证”。不能把 Beta 的模拟通过解释成目标运行时或 Telegram 已通过测试。

## 逐章核对

| 需求章节 | 结果 | 依据与限制 |

## 原文 40 个测试场景的覆盖映射

| 原编号 | 场景 | 自动验证与边界 |
|---|---|---|
| 1–4 | 无异常、有/无流量、无 Ping、无异常周报 | app、collector、weekly-report、simulated-flow；无 Ping 标数据不足仍发 |
| 5–7 | 单节点、数十节点、全部在线 | collector、weekly-report、statistics |
| 8–12 | 离线恢复、多次、跨日/跨周、未恢复 | events-storage/recovery/weekly-report 的事件与观察区间模型；不假装原生恢复配对 |
| 13–16 | CPU/内存/磁盘、到期、续费 | 统一 Alert/Expire/Renew 原生事件入口和渲染；具体供应商文本无法统一结构化 |
| 17–18 | 去重、未知类型 | events-storage；未知类型保留 originalType |
| 19–20 | 累计计数器与归零 | statistics；生产路径选用官方 traffic 增量，不依赖 counter 差值 |
| 21–22 | 缺失、重复时间戳 | statistics、collector；不完整标识/不丢整报 |
| 23–25 | Ping 频率不同、全部失败、无样本 | collector 按任务分离；不由任务频率推算失败；不确定 loss 不报告 0% |
| 26–28 | 日期边界、多时区/DST、无对比数据 | scheduler、calendar-config、statistics、weekly-report |
| 29–31 | 通知失败、未知、重试成功 | delivery、dispatch、simulated-flow；未知不自动重发 |
| 32–34 | 插件/服务重启、重复调度 | file-store、bundle、app、dispatch；发送中断恢复为 unknown |
| 35–37 | 手动补发、中断、部分分页成功 | app、dispatch、recovery；补发日期校验及分页状态模型 |
| 38–39 | 升级数据、损坏或写入失败 | recovery、events-storage、file-store；schema 1 保留，未知版本拒绝，不静默清空 |
| 40 | 全部数据不可用仍有失败提示 | runner、collector、simulated-flow |

覆盖映射不表示每个生产环境故障都被穷举。特别是在线观察精度、原生告警格式、通知模板是否重复转义及 Telegram 实际投递，仍依赖用户真实测试。

## 用户真实环境检查

1. 安装 ZIP、审批最小权限、启用、停用和再次启用。
2. 现有 Telegram 测试通知；确认自定义日报/周报均可收到。
3. 追加事件包装器后，原有即时告警继续正常；检查事件能进入插件且不回环。
4. 选已结束日期预览，对照节点的真实 traffic 增量与 Ping 任务。
5. 更改发送时间触发自动报告，重复触发不得重复自动发送。
6. 重启 Komari 后检查历史记录和数据；升级前导出备份。
