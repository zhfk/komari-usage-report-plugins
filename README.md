# Komari Daily & Weekly Reports

Komari 内部监控日报与周报插件，使用 TypeScript 开发并打包为普通 JavaScript。当前版本 **0.1.0-beta.1**，面向 Komari **1.6.1 及以上具有相同插件接口的版本**。当前稳定版与 SDK 已按官方 1.6.1 文档、源码及 SDK 核对；更高版本需重新确认。发布的是供真实环境测试的 Beta，未声称已通过实机验证。

每天默认北京时间 23:59 发送**前一个完整自然日**报告，例如 11 月 12 日发送 11 月 11 日日报；每周一 09:00 发送上一完整自然周报告。没有异常、流量为零、部分或全部数据缺失，都不会跳过报告。

## 安装

1. 从本仓库 Releases 下载 `komari-daily-weekly-reports-0.1.0-beta.1.zip`，不要上传 GitHub 自动生成的 Source code 压缩包。
2. 在 Komari 管理后台打开插件管理，上传该 ZIP。
3. 审批 `allowSystemRPC`（读取指标和发送通知）与 `allowRoutes`（管理操作和事件接收）；`node` 用于受限持久化目录和哈希。不申请执行命令、全磁盘访问、监听端口、Hook 或 HTML 注入权限。
4. 在插件的托管配置中检查时区、时间和节点筛选，启用插件。
5. 打开“监控日报与周报”管理页，先点击“测试通知”，再选已结束的日期预览并手动发送。前几份报告的在线率可能显示未知，因为插件没有安装前的在线观察历史。

默认所有可见节点参与；隐藏节点默认不包含，需管理员在配置中主动开启。节点 UUID 留空为全部，也可用逗号列出。所有内容模块、阈值、保留时间、排序、重试和补发参数可在官方托管配置表单修改。配置会在下一次检查时读取。

## Telegram 和事件采集

插件通过 `admin:sendNotification` 复用 Komari 现有通知设置，不保存或要求重新填写 Bot Token、Chat ID。请先确保 Komari 自身通知已启用且现有 JavaScript 通知脚本能调用 `sendMessage(message, title)` 发送 Telegram 消息。若现有脚本使用不同函数名，请按实际名称调整下面的转发包装器。

Komari 1.6.1 没有经核实的全局原生通知订阅接口。本插件的离线、上线、性能告警、到期、续费历史通过兼容转发方案采集：

1. 备份你现有的 Komari JavaScript 通知脚本。
2. 用随机生成的至少 32 字符字符串填写插件配置 `eventSecret`。
3. 将 [examples/notification-forwarder.js](examples/notification-forwarder.js) **追加**到现有脚本末尾，填写 Komari 可访问的 HTTPS 地址与相同密钥。通知脚本必须在同一作用域提供 `sendMessage`，原有 `sendEvent` 会被保留。
4. 开启 `eventForwarding`。在 Komari 发送一次测试通知并检查插件日志。
5. 确认已有即时告警仍能收到。移除追加部分即可恢复原脚本。

包装器仅转发事件类型、时间、消息及节点 UUID/名称，不转发含 Agent Token 的完整客户端对象。日报/周报/失败报告不会再次进入事件存储。转发失败记录日志，但原有即时通知仍继续执行。新增自定义报告事件直接调用现有 `sendMessage`，避免原有 `sendEvent` 的事件白名单丢弃报告。

报告正文已对动态文本做 HTML 转义。现有 Telegram 发送代码应使用 HTML `parse_mode`，且不要再对整段正文二次转义。包装器使用原有发送函数，所以应由你检查其 HTML 行为。原有通知模板最好只输出 `{{message}}`，或保留较短前后缀；默认每段正文预算 2800 字符，为外围模板留出余量。

## 数据语义及限制

- **流量**：使用官方 `traffic.up` / `traffic.down`（每次上报的流量增量、gauge、bytes），按 `sum` 查询并累加桶值；不累加累计计数器，不将速率当流量。按节点逐日查询，周报复用日聚合。重复、缺失、桶边界不对齐时提示估算或不可用。首尾覆盖率不是所有中间样本均存在的证明，原始采集缺口无法自动恢复。
- **Ping**：按节点和任务展示官方平均/最低/最高延迟、成功/失败及丢包百分比。`loss_approximate` 为真时，不声称能计算精确丢包；聚合历史可能混入失败样本而影响平均值。仅未降采样的原始样本才能统计超阈值次数，其他情况显示“无法计算”。不合并不同目标的平均值。
- **在线率**：每分钟观察 `common:getNodesLatestStatus`，只在连续两次有效观察之间累计时长，超过 150 秒的空档为未知，不计作离线。在线率、次数和时长均为观察估算；事件列表另外保留原生 Offline/Online 时间。无法还原安装前的准确在线历史。
- **告警**：保存原生 Alert 及原文，按时间展示和汇总。未提供恢复事件时，恢复时间未知；没有可靠严重等级时，不推断“最严重”告警。内容开关只对能从消息明确识别的类型分类，未知类型保守保留。
- **续费**：记录 Renew 事件，不将任意文本判定为续费成功。到期日期只使用节点的 `expired_at`。
- **发送**：`accepted` 仅表示通知 RPC 正常返回。Komari 通知全局关闭、未选择渠道、渠道脚本自行忽略消息时，也可能返回成功，所以不声称 Telegram 已送达。
- **时区**：Asia/Shanghai 和 UTC 使用内置转换；其他 IANA 时区需要宿主提供 `Intl.DateTimeFormat`。不支持时会明确报错。自然日边界处理夏令时的 23/25 小时日及午夜跳变。
- **事件完整性**：未启用转发、转发失败、原生通知关闭或插件停机均可能缺事件。没有事件记录不等于没有异常；报告说明采集范围。

## 失败、补发与记录

每分钟最多处理两份待发送/补发报告，默认追补过去 3 个发送日，可设为 0 关闭历史追补。日报和周报分别启停。每周期使用持久化去重键；手动发送独立记录，不阻止自动计划。明确在通知渠道调用前被拒绝的 RPC 请求采用指数退避，默认最多重试 3 次。

发送中的状态先落盘。出现超时、进程中断或可能已部分投递的错误时，将该页标为 `unknown`，阻止自动重发。请先到 Telegram 核实，再在管理页确认重复发送风险后重试未完成分页。已 accepted 的页不会再次发送。

## 备份、升级和卸载

数据保存在 Komari 提供的 `__storageDir__`，1.6.1 默认位于 `data/plugin-data/komari-daily-weekly-reports`。包含分日事件、在线观察、日报聚合、发送记录及有限日志；默认保留 180 天，不要求改变 Komari 的 3 天/10 天/25 天指标保存策略。底层已清理且未聚合的数据不能重建。

升级前点击“下载备份”，并备份整个持久化目录；上传新 ZIP 后重新启用。官方升级会保留数据目录。第一版存储 schema 为 1；未知未来版本会拒绝加载，防止静默清空数据。卸载会删除插件数据目录，请先导出和备份；若要仅停止运行，可禁用插件。恢复备份时停止插件后，将备份 `files` 中的 `path` 和 `data` 按相对目录恢复，保留或重新创建 schema 1 的 `meta.json`，不要导入不可信备份中的路径。

## 本地开发与打包

需要 Node.js 24、npm 和 Python 3，无需连接真实 Komari。

```sh
npm ci --ignore-scripts
npm run check
npm test
npm run package
```

安装 ZIP 及 SHA256SUMS 在 `artifacts/`。ZIP 根目录包含清单与 `script.js`，不包含 node_modules、测试凭据或源目录。构建使用 esbuild 输出普通 IIFE，并暴露全局 `load` / `unload`。SDK 用于清单校验，生产运行不依赖 npm。

GitHub Actions 对 main 上的代码更新执行类型检查、模拟测试、编译和打包；只有成功后才创建对应版本的预发布 Release 并上传 ZIP 和校验和。已存在的版本不会覆盖，下一次发版应同时更新 package 与清单版本。

测试覆盖和逐项需求核对见 [需求验收清单](docs/acceptance.md)，技术核查见 [兼容性记录](docs/compatibility.md)。测试未连接真实实例，仍需你在真实 Komari 中检查安装、通知脚本、Telegram HTML、数据语义与宿主时区支持。
